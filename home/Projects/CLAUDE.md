# ~/Projects 共通の指示（配下の全プロジェクトに適用）

## 紛らわしい名前の線引き：`SAPIX` と `STANDBY-SAPIX` は別系統

- **`~/Projects/SAPIX`** … SAPIX の **理科・社会**の教材PDFを抽出・連結して家庭の演習サーバ（Ubuntu）で配信するプロジェクト。**コベツバとは無関係**。
- **`~/Projects/STANDBY-SAPIX`** … コベツバ「StandBy」の **SAPIX版**。SAPIX **算数**の問題にコベツバの解説動画・ポイントを紐づける演習アプリ。こちらがコベツバ系統の幹。

名前が似ているため取り違えやすい。**コベツバ／算数の話に `~/Projects/SAPIX` を持ち込まない**こと。コベツバ系統は `STANDBY-SAPIX`（幹）・`KOBETSUBA-WEB`（コベツバWeb教材）・`STANDBY-YOSHIRI`（予シリ版）の3つ。

## 丸数字は使わない：`①` → `[1]` に統一（データ・コード・文書すべて）

紙面・PDF・OCR 由来の **丸数字（①②③…⑳㉑…）は、取り込んだ時点で `[1]` `[2]` … `[21]` 形式に変換する**。
会話やドキュメントの番号付けだけでなく、**アプリが保持・表示するデータの中身も対象**とする。

- **理由**：一般的なフォントの丸数字は ⑳(20) までで、㉑以降は環境により豆腐（□）になる。等幅フォントでは字面が小さく視認性も落ちる。OCR も丸数字を苦手とし（`⑮`→`⑬`、`⑳`→`㊄`、脱落など）、そのまま持つと誤りが混入する。
- **適用先**：問題文・小問ラベル・解答・テスト回のタイトル・OCR出力・JSON/DB の値・ドキュメント。
- **番号は OCR から読まない**：丸数字が崩れるため、**紙面構造から確定できる場合は位置で機械的に採番する**（例：1回20題・前半10/後半10と分かっているなら出現順に `[1]`〜`[20]` を振る）。
- **実装**：変換は共通ヘルパに集約し、取り込みパイプラインの出口で必ず通す。生成物（`data/*.json` 等）を直接書き換えるのではなく、**生成元を直して再生成する**。

## 答えを入力して採点する（**算数**の演習アプリ共通。STANDBY-SAPIX / KOBETSUBA-WEB / STANDBY-YOSHIRI）

⚠ **これは算数（中学受験）だけの決まり。数学には当てはめない。**
数学の答えは 文字式・`x=2, y=3`・`√`・`±`・場合分け・証明の記述などで、
**「数の並びを値で比べる」判定が成り立たない**（`x=2, y=3` と `2, 3` は別物、
`2√3` と `3.46` も別物、同じ式でも書き方が何通りもある）。
`seg-math-texts` など**数学のプロジェクトにこの節を持ち込まない**——
数学で採点をやるなら判定の考え方から別に決める。

演習アプリで**子が答えを入力し、機械が ○× を付ける**ときの決まり。
**目的は「本当にできたか・できなかったかが残ること」**——点数を出すことではない。
実装の正本は `STANDBY-SAPIX/standby_sapix/marking.py`、手順と経緯は
`STANDBY-SAPIX/docs/verify/ANSWER_BRIEF.md`、検算は `scripts/check_marking.py`。
別プロジェクトで作るときは**この3つを読んでから**、同じ規則で書く。

### ⚠ 迷ったら × にしない（これが根本）

書き方のちがい（単位を書かない・帯分数を仮分数で書く・ラベルを書かない）で × を付けると、
**できているのに間違いとして記録される**＝目的そのものを壊す。だから

| 入力と答え | 判定 |
|---|---|
| 数の並びが**同じ個数で全部一致** | ○ |
| 数の並びが**同じ個数で食いちがう** | × ← **自信のある × はここだけ** |
| 個数がちがう／数が出てこない／作図まじり／未入力 | **保留**（答えを見せて自分で ○×） |

- 比べるのは**数の並びの値**。帯分数 `2と4/7`・`2 4/7`・仮分数 `18/7`・小数を
  すべて同じ値として扱う（Fraction に直す）。**単位・ラベルは見ない**。
- `3:4` `9:40` は「3と4」に分ける（比・時刻がそのまま比べられる）。
- `cm2` の**肩の数字を数に数えない**。`[1]` `(3)` の**見出しも数えない**——
  ただし `[2]，[3]` のように**番号自体が答え**のときは数える（外すと数が残らないので見分けられる）。

### 画面の作り

- **単位は欄の外にあらかじめ出す**（サピックスの解答らんと同じ）。子は数だけ入れる。
  `時速[__]km`・`体積[__]cm³, 表面積[__]cm²`・`[__]分[__]秒`。
  **1つの値につき1つの欄**にすると「いくつ答えるのか」が見て分かり、保留に落ちにくい。
- ⚠ **答えは採点するまで画面に渡さない。**渡すと画面のソースに答えが載り、
  自分で解いたかどうかが分からなくなる。渡すのは「答えがあるか」と「欄の形」だけ。
- ⚠ 欄の周りに出してよいのは**単位と区切りだけ**（白名簿）。`五角形` `Bの店` `頂点C` のように
  **それ自体が答え**の言葉は伏せる。白名簿の語でも**語の途中では切らない**
  （`頂点C` を `点C` と切ると答えが出る）。
- 分数は「a/b」で**整数・分子・分母の3枠**に割る。分子分母にも**白い枠**を出す
  （線だけでは書ける場所に見えない）。整数を空にすれば仮分数。
  **帯分数の「と」は画面に出さない**（枠を並べれば帯分数。表示は数式に組む）。
- 採点するまで A/B/C/D（自己評価）を出さない。○なら A/B、×なら C/D、保留なら4つ全部。

### 記録

- **入力した中身をそのまま残す**（`typed`）。○×だけではどこで間違えたか分からない。
- 「答えを見る」は**空のまま採点**する扱いにして `seen`（見ただけ）として残す。
- テスト演習の無記入は `blank`（書けなかった）として ○×と区別する。

### 個別演習とテスト演習で入力のしかたを分ける

- **個別**……1問ずつ、その場で入力して採点。
- **テスト**……子は**紙（B4）で全問解く**。そのあと
  **問題番号と入力欄だけが並ぶ画面**（問題文は出さない）に書き写し、最後に一度だけ採点する。
  ○=B・×=C・無回答=D を**下書き**として自己評価に入れ、結果画面で押し直せるようにする
  （25問ぶん押させない）。

### iPad のペン入力は iPadOS のスクリブルに任せる

自前の手書き認識は作らない。Apple Pencil で**入力欄に直接書く**と OS が文字に変える
（iPadOS 14 以降。**ペンの世代は関係ない**——第1世代で可。
設定 → Apple Pencil → スクリブル に項目があれば使える）。
こちら側は**欄の作り**だけ整える: 高さ 44px 以上・幅 6em、文字 16px 以上
（16px 未満は iOS が入力欄に勝手にズームする）。値は採点時に読むだけなので、
スクリブルが入れた文字もそのまま拾える。

### ⚠ 画面(HTML)は毎回読み直す／JS は動かして確かめる

- テンプレートを起動時に1回だけ読むと、`uvicorn --reload` は `*.py` しか見ていないので
  **直したはずの画面が古いまま**出る。リクエストのたびに読む。
- **画面の JS は必ず一度動かしてから出す**（node で関数を呼んで吐く HTML を数える）。
  動かさずに出して「入力欄が2つ並ぶ」不具合をそのまま渡したことがある。

## PDF抽出に着手する前に必ず決めること：見開き／横並びページの扱い

PDF からの抽出・ページ画像化に取りかかる前に、**まずユーザーに「見開き／横並びページをどう扱うか」を確認し、方針を確定してから進める**こと。後から方針を変えると、全ページの分割・通しページ番号・図の紐付けがやり直しになる。配下プロジェクト（seg-math-texts の数学、PDF の理科・社会など）で実際に出たパターンを踏まえ、**着手時に次から選んでもらう**（複数該当もあり）。

1. **単ページ**：1 PDFページ = 1 実ページ（縦長）。分割しない。
2. **左右見開き = 2実ページ**：1 PDFページに実ページが左右2枚（横長）。→ 左右に分割し各々を1ページとする。
   - **分割方法**を選ぶ：
     - **(a) 機械的に中央 `w//2` で真っ二つ**（中身を一切見ない）。※ **seg-math-texts はこれを絶対ルール**とする。
     - **(b) レイアウト検出で段境界（中央の罫線／ガター）を見つけて分割**（PDFプロジェクト方式。中央線が無い等で効かないページは単段にフォールバック）。
   - **読み順**を宣言：標準は 左→右。
3. **1ページ内の2段組**：1実ページの中に2列（left/right）。→ 列ごとに分割し **左段→右段** の順に読む。OCR も列ごとに行い、`full`（左右結合）から一度に起こさない。
4. **左右で内容が別系統（クロス配置／反転綴じ）**：左ページと右ページで扱う単元・大問が異なる、または問題側と解答側が左右反転している。→ **作業の最初に「左＝○○側／右＝○○側」を明示宣言**し、**左右で別の大問を建てる**（同一大問にまとめない）。
5. **混在・不規則ページ**（見開きが表紙のように見える等）：自動分割に頼らず、**手動クリップ（region_app 等）で人が範囲指定**。

→ どれに当たるかを**着手時に必ずユーザーへ問い、決めてから**ページ画像化・抽出に進む。各プロジェクト固有の分割規則（例：seg は必ず 2-(a) の機械分割）は、そのプロジェクトの CLAUDE.md に従う。

## PDF・画像からの日本語テキスト抽出（共通ワークフロー）

紙面 PDF やスキャン画像からテキストを起こすときは、次の役割分担で行う。**NDL-OCR Lite を「検証用」ではなく「最初に使う一次抽出ツール」として使う。**

1. **日本語の本文抽出は、まず NDL-OCR Lite を使う（第一選択・一次抽出）。**
   - 実行: `ndlocr-lite <画像ファイル|画像ディレクトリ> <出力ディレクトリ>`
   - 出力: 出力dir に `<stem>.txt`（認識テキスト）/ `.json` / `.xml`。**CPUで約1秒/枚・GPU不要**。
   - 実体: `~/tools/ndlocr-lite`（専用 uv venv 同梱）。国立国会図書館（NDL）公式の ONNX 軽量OCR。
   - Python CLI（`src/ocr.py`）をラッパー越しに呼ぶ。手動用のデスクトップGUI版も別途あるが、自動化では CLI を使う。

2. **数式・記号・図・レイアウト依存の箇所は AI（vision）で起こす／検証する。**
   - NDL-OCR は `$x^2$`・`±`・分数・図・複雑なレイアウトを苦手とする（`x^2`→`x2`/`r2`、`±`→`土`、`0`→`Q` のように崩れる）。ここは AI が担当・補完する。
   - 逆に、細かい平文の日本語漢字は NDL-OCR が高精度で、AI（vision）の見落としを拾えることがある。**両者は相補的**——平文＝NDL一次、数式・記号＝AI、最終照合＝AI。

3. **コツ:** 2up（見開き2ページ）画像は、印刷1ページ単位に左右分割してから OCR にかけると精度が上がる。ツールのパスは ASCII のみ（全角パスでは起動しないことがある）。

> まとめ: **「平文の日本語＝NDL-OCR が一次抽出、数式・記号・図＝AI が担当、全体を AI で照合・校正」**。

## Python 環境
Python は終始一貫 `uv` を使う（詳細は `~/.claude/CLAUDE.md`）。外部ツール（ndlocr-lite 等）も専用の uv venv で動かす。

### Python の起動コマンドは `uv run python …` で統一（配下全プロジェクト共通）
`~/Projects` は uv ワークスペース（共有 `.venv`＝Python 3.14系。`pyproject.toml`/`uv.lock` は dotfiles 実体のシンボリックリンク）。スクリプトもアプリも **`uv run python <script>.py …`** で起動する。cwd 非依存で workspace の `.venv` を自動解決し、依存も自動同期される。

- **やらない**：素の `python3 xxx.py`（＝システムの **/usr/bin/python3 3.9系** を踏み、依存が無くて落ちる）／素の `python`（PATHに無い）。`.venv/bin/python` でも動くが、`uv run python` に寄せる。
- **docs・スクリプトの起動例も `uv run python` で書く**。シェルスクリプトで変数化するなら `PY=(uv run python)`（bash配列）＋ `"${PY[@]}" script.py`（`"$PY"` だと1語化して壊れる）。
- **対象外（uv を使わない正当な例外。`uv run` に変えない）**：
  - **インストール idiom** `uv venv` / `uv pip install --python .venv/bin/python -r …`（venv 作成・依存導入。`uv run` 前段なので別物）。
  - **Ubuntu 本番サーバ**（systemd の `/usr/bin/python3`・apt 導入の最小 venv 等）。
  - **vendored 外部ツール**（`vendor/ndlocr-lite` 等＝専用 venv）。
  - shebang（明示起動するので実害なし）。
- **新しい Python リポジトリ**は uv プロジェクト化（自前 `pyproject.toml`）か workspace member に追加してから `uv run` を使う（非プロジェクトのフォルダでは共有 venv を解決できない）。

## 実行コマンドは `projcmd`（Ctrl-G）のカタログに載る書き方をする

`~/Projects` 配下の「演習アプリ起動・Ubuntuへデプロイ・クロップ画面・PDF→OCR・M4へrsync」等の実行コマンドは、
**`projcmd`（zsh で `Ctrl-G`）が全プロジェクトから自動収集して fzf で選ばせ、コマンドラインに書き出す**。
実体は `~/.local/bin/projcmd`（dotfiles 管理）で、カタログは**保存すれば次回起動時に自動で作り直される**（手動なら `projcmd reindex`）。

**新しいプロジェクトを足したとき／既存プロジェクトのコマンドを追加・変更したときは、下の書き方に合わせる**こと。
合わせておけば登録作業は不要（自動で拾われる）。逆に、書き方を外すとカタログから消える＝「そのコマンドは無いもの」になる。

- **ドキュメントに書く場合**（README.md / DEPLOY.md / CLAUDE.md、`docs/` 以下も可・深さ5階層まで）
  - 言語指定を **` ```bash `**（または `sh` / `zsh` / `console`）にする。**` ```text ` のフェンスは拾われない**。
  - **1行1コマンド**。説明は**行末 `# 説明`** か、**直前の行の `# 説明`**。無ければ直近の見出しが説明になる。
  - 実行ディレクトリがプロジェクト直下でないなら、フェンスの先頭に `cd ~/Projects/<PROJ>/<sub>` を置く（以降その dir 扱いになり、選択時に `cd` が自動で前置される）。
  - 穴埋めが要るものは `<画像ディレクトリ>` のように `<...>` で書く（一覧に ✎ が付き「埋めてから実行」と分かる）。
- **シェルスクリプト**（`*.sh`）… 先頭のコメントに使い方を並べる。`#   ./deploy.sh setup        初回だけ：…` のように
  **「スクリプト名＋引数」→ 空白2つ以上 → 説明**、または `# 説明` 形式。行ごとに 1 エントリになる。
- **Python の画面もの**… `*_app.py` / `*_server.py` / `*_tool.py` / `crop_*.py` / `region_*.py` / `review_*.py` の命名にすると、
  ドキュメントに無くても `uv run python <path>` として拾われる（説明は docstring か先頭コメントの1行目）。
- **コンソールスクリプト**… `pyproject.toml` の `[project.scripts]` に書けば `uv run <name>` として載る。
- **ドキュメントに書けない・プロジェクト横断の定番**（M1→M4 の rsync、サーバ疎通確認など）… `~/.config/projcmd/commands.toml` に
  `[[command]]` を足す（dotfiles 管理＝M1/M4 共有）。ノイズを消したいときは同ファイル冒頭の `hide`（正規表現）に足す。
- **タグ**は内容から自動推定（`app deploy ubuntu m4 sync crop ocr pdf build check setup danger`）。
  日本語（演習アプリ／デプロイ／クロップ／同期…）でも引けるので、**説明は日本語で書いてよい**。

**確認のしかた:** `projcmd list -p <プロジェクト名>` に出れば OK。タグ別は `projcmd list -t deploy`、全文検索は `projcmd list -g <正規表現>`。
**Claude への指示:** 配下プロジェクトでコマンドを新設・変更したら、この書き方に沿っているかを確認し、必要なら `commands.toml` も更新して、
`projcmd list -p <プロジェクト名>` で載ったことを確かめてから作業を終えること。

**⚠️ フェンスの閉じ忘れに注意（エラーを出さずに壊れる）:** projcmd は Markdown を上から舐めて ` ``` ` の開閉でフェンスの内外を判定する。
**閉じ忘れ・余分な ` ``` ` が1つでもあると、それ以降のコマンドの「説明」が本来と違う見出しに紐づく**。
エラーは出ず一覧には載るので、`projcmd list` を見ても異常だと分からない
（実例: SEG の CLAUDE.md に孤立した ` ``` ` が1つ残っていて、クロップ画面の起動コマンドの説明が無関係な見出しの文言に化けていた）。
**CLAUDE.md や README を編集したら、`grep -c '^```' <file>` が偶数であることを確認してから作業を終える。**
奇数なら閉じ忘れ。「直後に足したはずの節が、ずっと後ろのコマンドの説明として出てくる」症状が出たら、まずフェンスを疑う。

## 用語：「leader＋キー」＝ tmux プレフィックス（Ctrl+a）
配下プロジェクトの会話で「leader F」「leader ○」と書いたら、**tmux のプレフィックスキーを押してから ○ を押す**操作を指す。この環境では tmux プレフィックスをデフォルトの `Ctrl+b` から **`Ctrl+a`** に変更済みなので、「leader F」＝ `Ctrl+a` に続けて `F`。「leader」＝ tmux の leader（＝プレフィックス＝ `Ctrl+a`）の意。
